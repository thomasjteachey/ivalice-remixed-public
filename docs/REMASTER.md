# The Ivalice Chronicles: where ReMixed's changes go

What the remaster's files look like, how mods change them, and where each kind
of ReMixed change has to go. Checked against the Steam version installed on
2026-11-02 with FF16Tools 1.13.3 and the FFT mod loader 1.7.5.

## Tools

Installed outside the repo, under `C:/Projects/Gamedev/tools/`:

| Tool | Version | Used for |
|---|---|---|
| [FF16Tools](https://github.com/Nenkai/FF16Tools) (CLI) | 1.13.3 | Unpacking `.pac` archives (`-g fft`), NXD ↔ SQLite. Its `Nex/Layouts/ffto/` folder describes all 245 data tables |
| [FFT mod loader](https://github.com/Nenkai/fftivc.utility.modloader) | 1.7.5 | Loads mods. Its `TableData/` folder has an XML template for every built-in table it can patch |
| [Reloaded-II](https://github.com/Reloaded-Project/Reloaded-II) | 1.31.0 | Runs the mod loader and code mods |

Gotcha: `FF16Tools.CLI list-files` writes `<pack>_files.txt` next to the
`.pac`, which puts files in the game folder. Move them out afterwards, or list
a copy.

## How the remaster stores the game

- **Two builds.** `FFT_classic.exe` with `data/classic/`, and
  `FFT_enhanced.exe` with `data/enhanced/`. Each has its own copy of every
  table and file, so a mod targets classic, enhanced, or both.
- **Archives** (same numbering in both folders):

  | Pack | Contents |
  |---|---|
  | `0000` | Backgrounds |
  | `0002` | `fftpack/`: the PS1 files (maps, effects, unit sprites, battle data) |
  | `0002.<lang>` | `fftpack/` text |
  | `0004` | `nxd/` data tables |
  | `0004.<lang>` | `nxd/` text tables |
  | `0005` | `script/`: event scripts |
  | `0006`–`0011` | Sound, system, UI, effects, font, shaders |

- **The PS1 files survive byte for byte.** These are identical to the vanilla
  US disc in both builds:
  - `fftpack/battle_bin.en.bin` (`BATTLE.BIN`)
  - `fftpack/world_world_bin.en.bin` (`WORLD.BIN`)
  - `fftpack/world_wldcore_bin.en.bin` (`WLDCORE.BIN`)
  - `fftpack/overlay/event_attack_out.en.bin` (`ATTACK.OUT`)
  - `fftpack/battle_entd1_ent.bin` to `fftpack/battle_entd4_ent.bin` (`ENTD1.ENT` to `ENTD4.ENT`)

  `event_test_evt.en.bin` (`TEST.EVT`) is bigger than the PS1's, and the game
  reads event scripts from `script/` instead.
- **The PS1 code isn't run.** Neither exe shows any sign of a MIPS interpreter
  or tables of PS1 code addresses, so the game logic is native. The remaster
  reads data out of those PS1 files. ReMixed's data inside them can be swapped
  in, but its code has to be rewritten ([MECHANICS.md](MECHANICS.md)).
- **The main exe's tables are compiled into the remaster's exe.**
  `SCUS_942.21` isn't shipped. Its tables (jobs, skillsets, abilities, items,
  statuses) live inside `FFT_classic.exe` and `FFT_enhanced.exe`, and the mod
  loader patches them there.
- **Default values are almost all vanilla PS1.** Compared with the mod
  loader's templates: 147 of 160 jobs, 498 of 512 ability learn rates and all
  128 weapons match the PS1 exactly. The 13 jobs that differ are Ramza's,
  Delita's and a few other story characters'. So ReMixed's changed values can
  be applied as they are, and the remaster's own tweaks survive wherever
  ReMixed didn't touch the same field.
- **Tables are bigger than the PS1's.** 174 jobs (PS1: 160), 261 items (254),
  85 equipment bonus sets (80), and War of the Lions skillsets at ids 224–226.

## Mod format

From the [mod loader docs](https://nenkai.github.io/ffxvi-modding/modding/creating_mods_fft/):

```
fftivc.<category>.<modname>/
├─ ModConfig.json
└─ FFTIVC/
   ├─ data/<classic|enhanced|combined>/      files replaced inside the packs
   │    ├─ fftpack/battle_entd1_ent.bin       (whole-file replacement)
   │    └─ nxd/overrideentrydata.nxd          (NXD edits are merged cell by cell)
   └─ tables/<classic|enhanced|combined>/    built-in table edits
        └─ JobData.xml                        (only the entries and fields you change)
```

Table XMLs should list only edited entries and fields, so mods don't clash.
The templates in the mod loader's `TableData/` folder document every field.
Status, element and equipment names differ from FFTPatcher's: for example
`Traitor` for Invite, `Vampire` for Blood Suck, `Doom` for Death Sentence.

## Mod loader gotchas

Found while testing with mod loader 1.7.5. `tools/build_mod.py` handles all of these:

- **Empty flags must be `0`.** Flag types with no `None` member (ability
  `Flags` and `AIBehaviorFlags`, status `CheckFlags`, item `TypeFlags`, the
  skillset extended-id flags) reject `None`. The table fails to load.
- **Skillset entries need both extended-id flag fields.** The ability-id
  setters update `ExtendAbilityIdFlagBits` and
  `ExtendReactionSupportMovementIdFlagBits`, and throw if those are missing,
  so write whole rows that include both.
- **Jump and Charge tables can't be patched.** Their ids start at 394 and
  406. Real ids are skipped as out of range, and 0-based ids crash the game at
  launch, because the loader looks rows up again by the real id. Both are held
  back until the loader is fixed. (ReMixed's values there feed its Jump rework
  and gun skills anyway, so they wait for that code too.)
- **The effect table's template names its root wrong.** `AbilityEffectNumberFilterData.xml`
  uses `<AbilityEffectNumberFilterData>` as its root, but the model the loader
  reads it into (with YAXLib) is `AbilityEffectNumberFilterTable`, like every
  other table's root. The build writes `<AbilityEffectNumberFilterTable>`. Its
  `EffectId` is signed, so "no effect" (0xFFFF) is `-1`.
- **Check `TableData/` before calling a table unsupported.** The names don't
  always say what's inside: the visual-effect table is `AbilityEffectNumberFilterData`
  (the name comes from FFT Mobile's symbols).
- **Keep table data in the loader, not in a code mod.** The loader reads each
  table's original values when it finds the table, after mod DLLs have started.
  A DLL that writes a table first makes its own values the "originals", which
  breaks the loader's merging of several mods' changes.
- **Installing while the game runs.** The game keeps mod files open, so the
  installed folder can't be deleted or fully replaced until it exits.
- **The log is the test.** On launch, the Reloaded-II console prints
  `Applying <Table> with N change(s)` for each table that loaded, and a red
  error with the table name for one that didn't. The same log is saved in
  `%APPDATA%/Reloaded-Mod-Loader-II/Logs/`.

## Code mod

`code/IvaliceRemixed/` is the C# half of the mod, for what no loader table
covers: ReMixed's mechanics. ReMixed's event scripts are written for Xifanie's
Event Instruction Upgrade, a PS1 hack ReMixed carries; its port is a mod of its
own, in its own public repo (https://github.com/thomasjteachey/eiu-ivalice-chronicles,
the submodule `code/eiu/`; mod id `fftivc.utility.eventinstructionupgrade`), which
ReMixed's ModConfig depends on. Its docs/ explain the instructions, its API and the
PS1 memory map. The upgrade exports `IEventInstructions`
(`code/eiu/src/EventInstructionUpgrade.Interfaces/`, a Reloaded-II controller): ReMixed's
`Patches/RemixedEvents.cs` gives it ReMixed's native routines, condition presets,
the dispatch tavern's variables and the scenario and text steps. What both mods
need of the remaster (the exe searched, hooks, battle units, the PS1 memory map,
GenerateUnit's unit making) is `code/eiu/src/IvaliceCore/`, a library each ships a copy of.
The build converts ReMixed's PS1 events with the upgrade's event tools (`code/eiu/tools/eiu_events`),
adding its own steps; `python -I code/eiu/tools/eiu.py disasm <event>.e` reads a built event as a script.
`tools/build_mod.py` compiles the C# (with the .NET 9
SDK) and adds `IvaliceRemixed.dll` to the mod once a patch needs it. Nothing
does yet, so it isn't shipped.

Tested on enhanced on 2026-11-02, with a first version that wrote the effect
table itself (since moved to the loader):

- Reloaded-II loads it through the mod's `ModDll`, and it starts before the
  loader scans for its tables.
- It found the table in `.rdata` by a byte pattern and wrote it after
  `VirtualProtect`. Reading the running game's memory from outside confirmed
  the values.
- It builds against `Reloaded.Mod.Interfaces.dll` from the Reloaded-II install
  (`Loader/X64/`), which Reloaded-II supplies at runtime, so it needs no NuGet
  packages.
- Its data comes from `Data/patches.json`, written by the build, with one
  section per exe.
- It finds everything by byte patterns in `.text` (like the loader's
  `Signatures/ffto.ini`) and cross-checks them, so a game update makes it log
  an error instead of writing to the wrong place.
- **Offline check:** `code/IvaliceRemixed.Check` maps the exe from disk
  without running it and applies the patches there. `build_mod.py` runs it on
  every build and stops if anything wouldn't apply, so the game doesn't need
  launching to test patterns and installs.
- **Hooks** come from Reloaded-II's shared hooks mod (`reloaded.sharedlib.hooks`,
  which the FFT mod loader also needs), through the `IHooks` interface in
  `code/eiu/src/IvaliceCore/Game.cs`. Detours are `[UnmanagedCallersOnly]` C#
  functions; Reloaded.Hooks moves each hooked function's first instructions to
  a trampoline and jumps from the entry (`jmp [abs32]` through a pointer in low
  memory). The mod's ModConfig depends on the shared mod.
- **An asm stub handed to Reloaded.Hooks as a detour goes near the hooked
  function** (`GameImage.AllocateCodeNear(function, size)`, not `AllocateCode`).
  The hook library allocates a small buffer of its own that has to reach both,
  and with a stub from anywhere that window can be a single 64 KB block, which
  another patch's stub can take: Passives' reaction rule failed so ("Unable to
  find memory location to fit MemoryBuffer of size 32 … between …") once Gains
  allocated its spillover stub. C# detours haven't run into it.
- **The offline check installs the real hooks** on its own copy of the exe
  (laid out from disk in private executable memory, since Windows won't make a
  resource-mapped exe executable), and **runs leaf steps through them** with
  made-up battle state: the HP damage step's self-test checks Adeptness and
  Vehemence against ReMixed's arithmetic; the end of turn, the post-move ability
  and the turn-over check run for First Move and Move-Cleanse. The copy's
  pointers aren't relocated and its imports aren't bound, so only code that
  doesn't follow stored pointers (settings, the renderer) can run there; the
  movement setup and the reaction code can't.
- Formulas log each distinct result once as a `trace` line in the Reloaded-II
  log (ability, inputs, damage before and after ReMixed's changes), for
  checking against a battle. `tools/test_formulas.py` points Ramza's chapter 1
  Dash and Throw Stone at a formula, in the installed mod only, so a new game
  can test it.

## Battle code (enhanced)

Mapped on 2026-11-02 with `code/ExeTool` (an Iced-based disassembler:
`dotnet run --project code/ExeTool -- <exe> <command>`). RVAs are for
`FFT_enhanced.exe`; the code mod finds them by pattern. The battle code is a
function-by-function rebuild of the PS1's, so PS1 routines and globals map
across, but some structures moved or grew.

**The whole exe as C** (2026-11-05): `python -I tools/decompile_game.py` runs
Ghidra 12.2 headless (installed at `C:/Projects/Gamedev/tools/ghidra_12.2_PUBLIC`,
Java 25) on the exe and writes all 20,359 functions as C to
`work/ghidra/decompiled/<rva>.c`, 64 KB of code per file, each function after a
`// ==== <rva> <name>` line (about 15 minutes, 37 MB). Ghidra names functions
`FUN_<address>` with the image base 0x140000000, so `FUN_1403dbe88` is RVA
0x3DBE88. Grep it for callers ExeTool can't see (calls through vtables and
function pointers) and to read a function whole; the Ghidra project
(`work/ghidra/project`) opens in Ghidra's UI for cross-references.

**Hooking: callers keep scratch registers.** The exe is built with
whole-program optimisation, so a caller can keep r10, r11 or xmm0–5 live
across a call to a function it knows doesn't touch them (the ability-bit
builder keeps r10 and r11 across its setter; the result step keeps a unit in
r11 across the EXP step; the battle loop keeps r11 across the end of turn). A
C# detour clobbers them all. Before hooking a function, run
`ExeTool <exe> liveregs <rva>`: it lists, for each direct caller, the scratch
registers read after the call before being written (rax is usually just the
result). When one is kept, hook through `Stub.KeepingRegisters` (r10, r11 and
xmm0–5 saved), or write the hook as a stub that only touches what the original
does. Patches in the middle of a function save everything, xmm0–5 included.

## Classic build support (mod loader 1.7.5)

Tested on 2026-11-02 with `tools/test_classic_override.py`, which adds the
ability override table to classic and nothing else.

- The loader rejects `nxd/overrideabilityactiondata.nxd` for classic as an
  unrecognized table, so **ability combat stats can't be changed on classic**
  this way.
- Built-in tables the loader finds in `FFT_classic.exe`, and so can patch:
  `AbilityData`, `AbilityJumpData`, `AbilityMathData`, `AbilityThrowData`,
  `AbilityTypeData`, `JobCommandData` (and its War of the Lions part),
  `MonsterJobCommandData`, `JobNeedLevelData`, `ItemData`, the weapon, shield,
  armor, accessory and consumable tables, `ItemOptionsData`, `ItemShopsData`,
  `StatusEffectData` and `CommandTypeData`.
- Tables it **can't find** in classic: `JobData` (jobs), `ItemEquipBonusData`,
  `AbilityChargeAimData`, `MapTrapFormationData`.
- **Why it can't find them.** The loader finds each table by searching memory
  for a run of the table's own bytes (`Signatures/ffto.ini`). Its job and
  Charge patterns hold enhanced's rebalanced values, which classic doesn't
  have. Searching the exes for the PS1 data finds all four tables in classic:

  | Table | In `FFT_classic.exe` (file offset) | Classic record | Loader expects | Fix |
  |---|---|---|---|---|
  | Jobs | 0x611C30 | 49 bytes, same as enhanced; 147 of 160 identical to the PS1 | 49 | New pattern (`tools/loader_signatures.py`) |
  | Charge | 0x613CC0 | 2 bytes, PS1 values (CT 4, 5, 6, 8…) | 2 | New pattern (`tools/loader_signatures.py`) |
  | Equipment bonuses | 0x664450 | 25 bytes, the PS1's (enhanced adds a Boost JP byte: 26) | 26 | Loader change: record size per build |
  | Move-Find | 0x6158C0 | 16 bytes, the PS1's (enhanced widens item ids: 24) | 24 | Loader change: record size per build |

  The 13 story jobs the remaster rebalanced (Ramza's, Delita's and a few
  others) differ from the PS1 in classic too. Enhanced additionally gives 73
  jobs Perfume and Hair Adornment.
- **What the classic build does.** With the job pattern applied
  (`tools/loader_signatures.py --apply`), classic gets jobs, skillsets,
  monster skills, unlock requirements, ability learn data, items, weapons and
  statuses. It can't take ability combat stats or equipment-bonus contents.
  It keeps the vanilla status-set order, because its abilities can't be
  updated to follow ReMixed's reorder. Items and weapons are pointed at
  whichever vanilla equipment-bonus or status set has the contents ReMixed
  wants, and abilities ReMixed reworked keep their vanilla AI flags. ReMixed's reordered status sets
  would also point vanilla classic abilities at the wrong statuses, so they'd
  have to be left out too.
- Launched directly from Reloaded-II, classic switches its text to Japanese a
  few seconds after starting. That's the game's own classic text-language
  setting, not a mod. Change it in classic's options, or start from enhanced
  and switch to classic in-game. Reloaded-II needs **both** exes registered for
  the in-game switch, or the loader stops with "Failed to locate application
  config".
